# GitHub / Gitee 双源发布与升级

已用真实附件验证两个平台匿名下载：加工器 3,098,624 字节，LiteHub 24,289,399 字节，BoHub 23,746,477 字节，NullHub 25,714,226 字节，以及 GitHub 正式 v0.9.103 安装器 8,154,440 字节。所有附件大小和 SHA-256 一致；客户端和匿名验证请求均不携带发布令牌。

## 两份 v2 清单

软件和资源分别使用 `hub-update-index-v2`、`mod-update-index-v2` 两个专用预发行标签。清单 JSON 存在 Release body，客户端通过匿名 Releases API 读取；每次发布还上传带 revision 的不可变 JSON 附件作为历史快照。这样无需把二进制或频繁变动的发布清单推入受保护的 main，也不依赖 Gitee raw 页的浏览器行为。

两边的清单内容一致，每个附件都有平台地址、精确大小和 SHA-256。先上传附件、验证匿名下载，再上传清单快照，最后更新清单指针。两平台不可能形成一个跨站原子事务，因此客户端会比较两份清单的 revision，选择最新兼容版本，并保留本地最高版本记录。同 revision 内容不同直接拒绝；镜像暂时落后不会造成降级。

旧 `resources/mod-resources-v1.json` 与原资源附件保留，不改写它们的含义。两个索引 Release 都是 prerelease，且不设为 latest，旧软件的 `/releases/latest` 仍只看到正式软件版本。

## 本地统一发布入口

日常请双击仓库根目录的 `release.cmd`，或运行 `.\release.ps1 -Target mods -Publish`。它会自动构建/打包、生成下述 spec、校验来源并调用底层发布器，支持原任务补传与软件正式版提升。首次配置、四类任务及完整命令见 [一键发布工作流](release-workflow.md)。以下是底层发布接口，供自定义集成使用。

依赖：Windows、Python、`requests`、GitHub CLI（已登录）、PowerShell。软件或资源都使用同一个命令：

```powershell
python scripts/publish-downloads.py --spec release-spec.json --output artifacts/publication
```

清单 revision 默认按 UTC 时间生成；需要精确重跑时指定 `--revision`。软件版本来自准备好的安装包对应的源码版本，资源版本来自资源发布标签，不用构建时间冒充程序版本。文件由外部构建一次，发布脚本核对安装器内嵌版本，只读取这些确定的字节并分别上传两边。失败重试必须复用同一文件；内容变化必须增加版本。

软件 spec 示例：

```json
{
  "kind": "software",
  "product": "D2RHub",
  "platform": "windows-x86_64",
  "assets": [{
    "id": "hub",
    "version": "0.9.104",
    "file": "artifacts/D2RHub_0.9.104_x64-setup.exe",
    "release_tag": "v0.9.104"
  }]
}
```

资源 spec 沿用 `resources/mod-resources-v2.json` 的兼容字段，改 `kind` 为 `resources`，每个变化的 asset 增加 `file`、`release_tag`。首次发布必须包含四个资源；以后只列变化项，脚本从当前索引继承未变化项，也可通过 `--previous` 指定已保存的 v2 清单。修复镜像时列出需要补传的资源并使用更高 revision。

每个资源版本另有不可变 `id-version.identity.json`，防止换文件名后绕过同版本内容约束。相同附件只校验、不重复上传；同版本不同大小或摘要直接拒绝。资源 `sequence` 在更换版本时递增，与清单 revision 分离。发布脚本保留报告，部分失败时输出“镜像未完成”，可以补传。

发布配置放在 `%LOCALAPPDATA%\D2RHub-Publisher\config.json`，令牌单独以 Windows DPAPI 加密保存到同目录的 `gitee-token.dpapi`。只能由同一 Windows 用户解密；Python 直接调用 DPAPI，令牌不经过子进程参数、stdout、Git 或客户端。GitHub 认证使用 `gh` 的本地凭据。

正式软件发布还需要正常的代码审核和构建：发布脚本默认创建非 latest 的预发行版供验证，确认后才把软件版本提升为正式发布。资源索引和资源包永远不提升为软件 latest。

## 客户端选源与故障切换

设置 → 启动策略 → 下载源：自动 / 优先 Gitee / 优先 GitHub。

- 手动选择直接决定优先级，不访问地区服务，失败仍切换备用源。
- 自动模式通过短超时的公开国家查询判断网络出口；CN 优先 Gitee，其余优先 GitHub。仅缓存国家码和优先平台 7 天，不保存返回的 IP。
- 地区服务不可用时并行轻量探测两边索引可用性，缓存结果 1 小时。地区识别不会成为下载前提。
- 检查版本时读取两份小清单，避免“可访问但落后”的镜像遮住新版本；任一来源失败，另一来源仍可独立完成检查。
- 文件下载按优先级依次尝试，每个平台最多一次。连接/响应超时、连续 20 秒无进度、404、大小或 SHA-256 不符都会切源；重新下载，不跨平台续传。主动取消立即停止，不切源。
- 临时文件校验通过后才发布到正式路径。错误网页、截断文件或登录页不会成为可执行安装包。

## 三层兼容约束

| 层次 | 约束 |
| --- | --- |
| 软件安装器 | schema 2、D2RHub 产品标识、Windows x86_64、正式 SemVer 且严格高于当前 Hub，下载文件内嵌的 Windows 版本必须与清单一致 |
| Hub ↔ 加工器 | 资源目录的 Hub 版本范围，加上 `v7-r25-r28-lightweight-v1` 协议/配方通道、精确文件摘要、真实 `--version` 与现有加工输出校验 |
| Mod ↔ 游戏 | 固定方案身份、资源 sequence、生成清单与本机激活游戏数据版本一致 |

当前资源目录面向 `0.9.104 <= Hub < 0.10.0`，加工器为 `1.4.0-beta.17`，三个 Mod 为数据版本 `93854`。加工器的软件版本、产物配方和游戏数据版本是不同维度，不能互相替代。破坏性协议变化必须创建新兼容通道并升级 Hub，不能向旧通道直接投放不兼容程序。

检测到新加工器后，已验证且兼容的受管旧加工器仍可使用，用户选择更新后再切换。加工器按版本和摘要隔离保存，避免替换正在使用的 EXE；损坏的同版本目录可通过事务替换修复。旧安装目录旁的加工器只作为迁移提示，不覆盖安装器拥有的文件。

旧 Hub 无法在代码不变的情况下获得 Gitee 能力：GitHub 可用时仍通过旧正式更新流程升级；GitHub 不通时，先从 Gitee 手动下载新版完整 Hub 安装包完成一次过渡，之后使用双源检查和下载。旧 v1 Mod 清单不被升级脚本破坏。

## Mod 原位更新

Mod 仍安装到所选国服/国际服游戏的 `mods\名称`，账号启动参数不变。安装记录保存资源版本、sequence、下载摘要和目录内容摘要。

- 已受管、未修改的Mod 可以原位升级。安装前核对目录内容，游戏运行时禁止替换。仅忽略 `-txt` 从同目录 TXT 重新生成的 BIN 缓存；修改 TXT 或独立 BIN 仍会被保护。
- 以前安装、没有记录的Mod，只有与发布原始文件逐项一致时才接管。生成清单中的旧机器绝对路径不影响匹配。
- 检测到加工清单、手动修改或未知来源时保留现有 Mod。应另存用户版本，或用新Mod 重新加工；不自动用纯净包抹掉定制功能。
- 在同一磁盘准备完整新目录、落盘、写恢复记录，再将旧目录移为备份、新目录移入原位置。失败恢复旧目录，进程中断后在下次启动或安装前恢复。成功后保留备份，不自动删除用户唯一的旧版本。

## 自动检查与软件安装

沿用“每日检查更新”开关，同时检查软件、已安装加工器、已安装Mod；关闭开关后两者都不自动联网检查。手动检查始终可用。两类检查独立，网络失败不记作当天已完成。

自动检查只通知，不自动下载、覆盖、重启游戏或安装软件。软件流程为：发现新版本 → 用户下载 → 显示来源及切换进度 → 验证大小和摘要 → 用户点击安装 → 重新校验文件及安装器实际版本 → 启动完整安装器并退出 Hub。后台任务进行中时阻止安装器启动。
